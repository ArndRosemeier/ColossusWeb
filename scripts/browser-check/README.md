# `scripts/browser-check/` — driving the REAL app in a REAL browser

**Why this exists.** Twice now, a fully green gate has hidden a defect that only a
browser could see: `fetch` held on an instance and called as a method (every browser
refuses with `Illegal invocation`, while every stub in the suite is
receiver-insensitive), and a lobby that subscribed to a no-op external store so every
poll tick's data was dropped. A DOM-free suite cannot see either. The rule this
encodes: **a UI behaviour is not proven until it has been observed in a browser.**

**Provenance.** These files are salvaged from the S4 writer's own scratch
(`worktrees/liveness/.browser-check/`, untracked) because they worked and are worth
keeping. They are an **unreviewed starting point**, not a finished tool: paths and
seeds are hard-coded to that slice's scenario, and nothing here is wired into the
gate. Treat it as a recipe to copy, not a command to trust.

- `cdp.py` — a small DevTools-Protocol driver (its own WebSocket; no library). The
  page gets WALL-CLOCK time, which `--dump-dom` does not: that dumps when the first
  paint settles, before the app's first fetch returns, so the lobby looks empty.
- `harness.py` / `run.sh` — render the built app against a seeded fake store.
- The Chrome tree is killed in `finally`, so it dies on the failure path too.

**The method that worked, and it is the point of the directory:** build the app with
`VITE_SERVERSTORE_URL` pointed at a fake store you control, drive the real UI over
CDP, and then **change the store from OUTSIDE the app** and observe the UI react with
no click, no refresh and no reload. That is how a two-browser scenario becomes one
browser plus one `PUT`.

**S5's check, and the second method (`s5-busy-wording.py`).** S4 answered the store
with a fake HTTP server on the same origin. S5 answers it with the DevTools Protocol's
`Fetch` domain instead: `Fetch.enable` on `https://store.futuremagic.de/*` and
`Fetch.fulfillRequest` for every paused request, so the app's own transport, poll loop
and React render are the code under test while the "store" is whatever this script
says it is. Run it after a build: `python3 scripts/browser-check/s5-busy-wording.py`
(it serves `web/dist` itself and exits non-zero, naming each failed statement). Exit 0
means the real DOM said `the store is busy — slowing down, retrying in 60s` after a
`429` that carried `Retry-After`, and that the FIRST listing on the wire was
`?prefix=game.` with the key in `Authorization` and nowhere else. Two traps cost a run
each and are already handled here: the store's CORS **preflight** must be answered by
the script (it is a request to the same origin, it carries no key, and a real store
never rate-limits one), and `Fetch.enable` must be armed BEFORE the first navigation
(the app validates a stored key the moment it mounts).

**S6's check, and the third method (`s6-adoption-roll.py` + `web/scripts/browser-check/`).**
S6's symptom is what the BOARD shows after a remote snapshot changes the roll, so the
check drives a real adoption and reads the board. It needs a real game state, and a
hand-written one would be a second implementation of the movement rules — so the
fixture is GENERATED by the engine:
`cd web && npx vitest run --config scripts/browser-check/vitest.config.ts` runs
`gen-fixture.test.ts` (outside `src/`, so the gate never runs a file that writes to
disk) and writes `fixture.json` here: two snapshots built through the real engine (a
turn-1 split, then the next player's roll), with the LEGAL SETS the engine itself
computes. Then `python3 scripts/browser-check/s6-adoption-roll.py` (after
`npx vite build`) serves `web/dist`, seeds localStorage with a made-up key plus the
active game, and lets the app resume it; the script selects a stack by clicking the
real DOM, then SERVES the second snapshot and watches the app adopt it with no click,
no refresh and no reload.

Three things are worth copying from this one:

  * **`--force-prefers-reduced-motion`** — a move click otherwise starts a tween and
    queues the command, so "the move was accepted" would time out on the animation's
    clock rather than on the rule.
  * **A click on a NON-legal hex is the board's DESELECT gesture**, not a refusal: the
    "illegal hex moves nothing" statement must be checked AFTER the legal move, or it
    clears the selection the next statement needs.
  * **The app's own autosave is a readable view of the adopted state.** `legalHexes`
    is write-only in the shipped code (the board derives its rings live from
    `getMovesForSelected`), so the DOM alone cannot distinguish a stale copy from a
    recomputed one. The check reads `colossusweb.save.v1` — the state the app
    genuinely holds and would publish — and THAT is what goes red under the defect
    (`['100', …45 hexes]` where the engine's roll-3 set is `['127','29','33']`), while
    the rings follow the adopted roll either way. Both are asserted; neither is
    inferred. This is also why the check's fixture writes `turnNumber` and the
    snapshot header's `turn` from the SAME round: `publishSnapshot` names a snapshot
    `(state.turnNumber, seq)`, so a fixture whose header and state disagree makes the
    app publish a name that sorts BEFORE the snapshot it just adopted.

**S7's check, and the fourth method (`s7-move-gate.py`).** S7's symptom is what the
board SHOWS with a non-active legion selected, so this check is the OWNER'S OWN data,
not a generated fixture: the read-only probe's `fixture.json` (his 21 store objects,
sha256-verified there) is COPIED to `s7-fixture.json` here — gitignored scratch, never
committed — and served by a fake store on the same origin (the app is built with
`VITE_SERVERSTORE_URL=/storeapi` and every request is answered by the script). The
keys are made-up strings containing `testonly`; nothing leaves the box. Build and run:

```
(cd web && VITE_SERVERSTORE_URL=/storeapi npx vite build \
    --outDir ../scripts/browser-check/s7-dist --emptyOutDir)
python3 scripts/browser-check/s7-move-gate.py host    # his seat, his Move phase
python3 scripts/browser-check/s7-move-gate.py guest   # seat 1 on the opponent's turn
```

It asserts the DOM, not a function: **host** (15 statements) that his own stack paints
exactly the engine's roll-3 destinations, that an OPPONENT's stack paints no legal ring
but does paint the preview, that a click on a previewed field **does not deselect**,
**does not make the fields vanish**, **publishes nothing** and puts a sentence on the
message surface, that a plain hex still deselects, and that a legal move still moves
and publishes exactly one snapshot; **guest** (5 statements) that NO actionable field
is painted and a click surfaces a reason. Two traps this one encodes: the lobby's
**Enter game button is `disabled` while the lobby refreshes**, and `element.click()` on a
disabled button is a silent no-op, so the check retries until the board renders; and the
owner's snapshot chain must be seeded from his LAST snapshot for the host mode and only
up to seat 1's turn (then served p0's snapshots) for the guest mode, or the seat under
test is not the one the brief names.


**S8's check, and the fifth method (`s8-engagement-choice.py`).** S8's symptom is
what ONE SEAT is shown while the OTHER owes an answer — the owner clicked "Fight!"
and got the battleground while the defender was never asked to give up. No
DOM-free test can see "whose client has which button", so this one runs **one
browser per SEAT** and reads the overlay each of them is looking at. The fixture
is GENERATED by the real engine (`web/scripts/browser-check/gen-fixture-s8.test.ts`)
and round-tripped through the app's OWN parsers, so the state cannot drift from
what a real client would accept:

```
(cd web && npx vitest run --config scripts/browser-check/vitest.config.s8.ts)
(cd web && VITE_SERVERSTORE_URL=/storeapi npx vite build --mode test \
    --outDir ../scripts/browser-check/s8-dist --emptyOutDir)
python3 scripts/browser-check/s8-engagement-choice.py host    # seat 0, the ATTACKER
python3 scripts/browser-check/s8-engagement-choice.py guest   # seat 1, the DEFENDER
```

**host** (13 statements): the app resumes on the PENDING engagement, `button.fight-btn`
opens it, exactly one snapshot is published and it is the open engagement with no
battle; the overlay says `Waiting for … to choose: stand and fight, or flee`; there is
**no** `Fight!` and no defender control on this client; and a FORCE-DISPATCHED
`proposeAgreement{fight}` — fired through the app's own commit path — does not start a
battle, shows no battle board, puts the refusal sentence on the message surface and
publishes no game change. **guest** (12 statements): the defender's client is the one
asked (`Stand and fight` + `Flee`, no `Fight!`), pressing Stand closes the window in the
shared state, PUBLISHES that answer for the attacker, and leaves no window to answer.

Three traps this one encodes, beyond `--mode test`: the engagement control carries the
two marker chits and **not** the words "Start engagement", so it is found by
`button.fight-btn`; a REFUSED command still publishes one snapshot carrying UNCHANGED
state (the commit path publishes on any new object), so the statement is about the
state's content and not about the PUT count; and the check's bundle must be built by
hand (the same gap S7 records) — the production bundle deliberately drops the
`window.__colossusDispatch` handle it needs.

**S9's check, and the sixth method (`s9-game-hygiene.py`).** S9 is TWO features, and both
are UI flows whose most important cases only a browser can see:

  * GIVE UP must be **offered, confirmed, and then actually end the game** — and it must be
    **DISABLED inside a battle**, so a DOM-free suite can pin the engine's refusal but not
    "the control is on screen, greyed, with the reason beside it".
  * DELETE's EXPECTED outcome today is a **store refusal**: ServerStore makes `delete`
    opt-in and the owner's live keys are `read,write`, so "`403`, LOUD, and NEVER a claimed
    success" is a statement about what is on screen and about which objects are still in
    the store afterwards.

The fixture is GENERATED by the real engine (`web/scripts/browser-check/gen-fixture-s9.test.ts`)
and round-tripped through the app's OWN parsers, so nothing here re-implements a rule or a
name. It writes THREE things: a started two-human game plus a snapshot of that same game
with a battle RUNNING; a game the caller created and joined (with snapshots); and a game
created by another key which the caller never joined, so "not offered, not touched" can be
asserted. `delete` is switched from the OUTSIDE with `S9_DENY_DELETE`/`S9_PERMS`, so the
same check proves the refusal AND the successful delete without touching the app:

```
(cd web && npx vitest run --config scripts/browser-check/vitest.config.s9.ts)
(cd web && VITE_SERVERSTORE_URL=/storeapi npx vite build --mode test \
    --outDir ../scripts/browser-check/s9-dist --emptyOutDir)
python3 scripts/browser-check/s9-game-hygiene.py delete-denied     # 14 statements
python3 scripts/browser-check/s9-game-hygiene.py resign            # 15 statements
python3 scripts/browser-check/s9-game-hygiene.py in-battle         #  7 statements
S9_DENY_DELETE=0 S9_PERMS=read,write,delete \
  python3 scripts/browser-check/s9-game-hygiene.py delete-granted  #  6 statements
```

**delete-denied** (the owner's TODAY case): the caller's own game is offered a delete and one
they never joined is NOT; the confirmation NAMES the game and counts snapshots, players and
the record; pressing it shows the store's own `forbidden` + `key is not allowed to delete
objects`, says **Not deleted.**, counts what remains (all seven objects, the record among
them), adds *"ask the operator to grant the delete permission"*, and the store is verified
object-for-object to be untouched. **delete-granted**: everything of that game goes, the
**record is last** (proved by the app's own DELETE order), the other game is byte-for-byte
identical, and the confirmation clears. **resign**: the control is enabled outside a battle,
the first press asks and names the player and the legions, the second ends the game — the
resigner is dead, every legion of theirs is off the board, the opponent has won and the top
bar says so, and the log never claims a Titan was slain. **in-battle**: the control is still
SHOWN (never silently absent) but disabled, with the engine's own sentence beside it, and a
force-dispatched `resign` through the app's own commit path is refused with nothing changed.

Two traps this one encodes, beyond `--mode test`: the `in-battle` mode resumes into a BATTLE,
so the board probe must accept the battle board as well as `svg.master-board` (a
`svg.master-board`-only wait times out on a page that is rendering perfectly); and the delete
modes must write NO active-game pointer, or the lobby would resume a game and there would be
no game list to delete from.
